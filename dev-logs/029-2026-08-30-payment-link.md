# Dev Log 029 — `confirm_with_deposit` hands back a payable link

**Date:** 30 August 2026
**Trigger:** Handoff from the architecture session (dev-logs 001/002/005/007/012): the demo needs an
agent that can hand a human a real link to pay, and nothing in the codebase produced one.
`confirm_with_deposit` created Razorpay orders server-side and polled for up to 5 minutes for a payment
to land — but never surfaced the order anywhere a human could actually reach Checkout. The only way the
deposit fixtures in dev-logs/006 ever got paid was a human reading an `order_id` off the Razorpay
dashboard directly.

---

## The empirical answer: can Razorpay Payment Links do the authorisation legs?

The user asked specifically whether the Payment Links API could replace a custom checkout page. Checked
live against this account's test keys (not inferred from docs) once fresh keys landed — the old ones were
returning `401 Authentication failed` for most of this session.

**No, on two independent counts, both confirmed by live API rejection:**

1. `POST /v1/payment_links` with `payment: { capture: "manual" }` → `{"error":{"code":"BAD_REQUEST_ERROR","description":"extra fields sent"}}`.
   Razorpay's own docs say capture settings apply only to the Orders API — this is the live confirmation.
2. `POST /v1/payment_links` with an existing `order_id` attached → the same `"extra fields sent"`
   rejection. A payment link cannot be attached to an order Latch already created; it always creates and
   owns its own order internally.

Both blockers the architecture session's brief predicted turned out to be real, and stronger than
"probably" — Payment Links reject the request outright, not merely ignore the field. `short_url` creation
itself works fine (`payment_links.create` with a plain amount returns a real `https://rzp.io/...` link
instantly), so Payment Links would have worked for the deposit leg alone. They cannot do the two
authorisation legs, which are the actual B1/Idea-3 story — the deposit-only case isn't interesting enough
to build a second mechanism for. **Option B — a served checkout page against our own order, using the
Orders API directly — is the only option that covers all three legs. Not a preference; the alternative is
structurally impossible for two independent reasons.**

## The other open design question: does `confirm_with_deposit` keep blocking?

Flagged back to the architecture session before touching the money path, since getting this wrong meant
redoing it. The literal deadlock: a tool that blocks for 5 minutes waiting on a payment can never hand a
link to anyone, because nothing is returned until the wait is over. Confirmed: restructure it to return
fast.

**What changed, concretely:**

- `PaymentProvider`/`PaymentRail` (`src/ports/`): `captureDeposit`/`authorize` — one long-blocking
  create-then-poll-for-5-minutes call — split into `ensureDepositOrder`/`ensureAuthorizationOrder` (fast
  create-or-find, no waiting) and `pollDepositCapture`/`pollAuthorization` (a short, bounded poll —
  `DEFAULT_QUICK_POLL_TIMEOUT_MS`, two ticks at 3s — that returns `undefined` rather than throwing a
  timeout when nothing has landed yet). `PaymentTimeoutError` is gone from both ports — "not paid yet" is
  the ordinary case here, not a failure, so there's nothing left that throws it.
- `RazorpayPaymentProvider`/`ManualCaptureRail` implement the split for real; `ReservePayRail` gets the
  same two-method shape as throwing stubs, unchanged in spirit; `FakePaymentProvider`/`FakePaymentRail`
  gained a `'pending'` scenario (replacing `'timeout'`) and `completeDeposit`/`completeAuthorization` test
  helpers that model a human paying a previously-issued link.
- `confirm-with-deposit.ts` (full rewrite): gate check unchanged. Then, outside the row lock as always
  (never hold a DB lock across a network call): ensure every needed leg's order exists (parallel,
  `allSettled`), then a short poll per leg (same). If the mandatory deposit hasn't landed, record
  `PAYMENT_REQUESTED` and return `{status: 'PENDING', pendingPayments: [...]}` — pay links, one per
  outstanding leg, still `HELD`. If it has, finalize exactly as before (append `DEPOSIT_CAPTURED` +
  whichever optional legs landed + `BOOKING_CONFIRMED`).
- `ConfirmWithDepositResult` is now a discriminated union on `status` (`'CONFIRMED' | 'PENDING'`), not one
  shape with everything optional — a caller can't accidentally read `.deposit` off a `PENDING` result
  because the type doesn't have that field on that branch. `PENDING` is a **result shape**, never a
  booking status — no new state was added to `BookingStatus`, `fold()`, or the schema's status enum
  (docs/03-domain-model.md §3 has a note now explaining this, matching the precedent that section already
  set for `NO_SHOW_ELIGIBLE`'s own projection/fold divergence).
- **The old 5-minute in-process wait is gone; `CONFIRMATION_CLAIM_WINDOW_MS` (still 5 minutes, unchanged
  constant) now does double duty as the actual timeout mechanism.** Every confirm attempt — including a
  `PENDING` one — bumps `holdExpiresAt` by 5 minutes from `now`, exactly as it always did. If a human
  never pays and the agent never retries, that window eventually lapses and the **existing** hold-expiry
  worker reclaims the row — the identical "leaves it HELD, never refused" invariant `PaymentTimeoutError`
  used to guarantee, now enforced by infrastructure that was already built and tested instead of a
  bespoke `while` loop. Confirmed this doesn't touch `one_live_booking_per_slot` or the worker's own claim
  query — both already only care about `holdExpiresAt`, not about which code path bumped it last.
- **`IdempotencyStore` semantics**: `CONFIRMED` still `.put()`s (cached, replayed on retry). `PENDING`
  now `.release()`s instead — it is not a terminal outcome, so a retry with the same key must re-claim and
  re-poll rather than replay a stale link set.
- **A new, non-money event: `PAYMENT_REQUESTED`** (`src/domain/events.ts`), appended when a `PENDING`
  result is returned. Carries `legs: {leg, orderId, amountPaise, label}[]`. Not a `MoneyFields` event —
  no rupee moved. Exists so the trail can explain the otherwise-unaccounted-for gap between
  `POLICY_ACKNOWLEDGED` and `DEPOSIT_CAPTURED`: "we asked for ₹300 at 14:04, they paid at 14:09." New DB
  column `bookings.pending_payment_legs` (jsonb, migration `0015_payment_link.sql`, hand-written to match
  this project's own convention for schema changes `drizzle-kit generate` can't cleanly diff against —
  same reasoning migrations 0001/0010/0011/0013/0014 already used) — cleared to `null` the instant the
  booking actually confirms.
- **The pay page**: `GET /pay/:bookingId/:leg` on `latch-viewer` (`audit-trail/server.ts`), not
  `merchant-api`. Resolves amount/orderId/label from `bookings.pending_payment_legs` server-side — the URL
  itself carries only `bookingId` and a leg name, never an authoritative amount (a peer-review correction
  before this was built: `?amountPaise=` in a query string is attacker-displayable even though Razorpay
  would still charge the real order amount underneath it — "the page said one thing, the rail did
  another" undercuts the exact B1 claim this project exists to make). Mounted on `latch-viewer` specifically
  because it's the one server with Helmet's CSP already off (`security-headers.ts`'s own comment) —
  Checkout.js is a cross-origin script load a default CSP blocks, and reshaping `merchant-api`'s
  JSON-only, Bearer-gated contract for one HTML route wasn't worth it. New `PAY_PAGE_BASE_URL` env var
  (`config.ts`), read by `build-deps.ts` into `AppDeps.payPageBaseUrl` (optional — falls back to
  `http://localhost:${AUDIT_TRAIL_PORT}` so the ~20 test files that construct an `AppDeps` and never touch
  this feature don't all need to name it).
- **MCP tool description** for `confirm_with_deposit` rewritten to tell the calling agent exactly what to
  do with a `PENDING` result: relay the links verbatim, ask the human to pay, retry with the same
  `bookingId`/`idempotencyKey` once they say they have.

## A real bug this caught, live — not found by any test

First live run returned a correct `PENDING` result with three real pay links. Checking Razorpay's own
dashboard state after found **six** orders for one booking, not three — every leg had a duplicate.
Root cause: `pollDepositCapture`/`pollAuthorization` were each internally re-calling
`ensureDepositOrder`/`ensureAuthorizationOrder` to re-derive the order (reasoning at the time: "idempotent
receipt lookup, cheap, harmless"). It is not harmless. Razorpay's `orders.all({receipt})` lookup is **not
immediately consistent** with a create that just happened milliseconds earlier — verified directly: a
receipt lookup run immediately after creating that exact order returned zero results; the same lookup
five seconds later found it. Two calls to "find-or-create" within the same confirm attempt, a few hundred
milliseconds apart, raced that lag and both concluded "not found" — both created a fresh order.

Fixed at the port level, not patched over: `pollDepositCapture`/`pollAuthorization` now take the
already-created order directly (`DepositOrder`/`AuthorizationOrder`) instead of re-deriving it from
params. There is no second lookup left to race — the class of bug is gone, not just this instance of it.
Also closed a second exposure of the same root cause: a retry (agent calls `confirm_with_deposit` again
after the human says "I've paid") used to call `ensureXOrder` again too, which would hit the exact same
lag if the retry landed within a few seconds of the first attempt. Since the order's id is already
sitting in `bookings.pending_payment_legs` — a strongly-consistent read against our own Postgres, not
Razorpay's — a retry now checks there first and only calls the rail if genuinely nothing is recorded yet.
Verified live, twice: a fresh booking gets exactly 3 orders; an immediate retry (same idempotency key,
well inside the lag window that produced the bug the first time) still shows exactly 3, confirmed both by
direct receipt lookup and by the identical link set coming back from the retry.

This is exactly why the payment-link check plan called for testing against real Razorpay rather than
trusting the port design on paper — the fakes could never have caught this, since `FakePaymentProvider`'s
in-memory maps have no equivalent consistency lag to reproduce.

## What was verified live versus what could not be

**Verified directly, against real Razorpay test mode and a real browser:**
- All three legs' orders create correctly (deposit: `payment_capture: true`; both authorisation legs:
  `capture: "manual"`, `manual_expiry_period` at the 5-day max) — confirmed via direct Razorpay API reads
  of the created order objects, not just inferred from the request payload sent.
- The `/pay/:bookingId/:leg` page renders the correct label/amount/booking id for all three legs, 404s for
  an unknown booking, and correctly reflects `pending_payment_legs`.
- Clicking Pay opens real Razorpay Checkout.js, in Test Mode, against the correct order and amount —
  confirmed visually via a real (non-headless) browser.
- The duplicate-order bug and its fix, as described above.

**Not completed, and not completable by this session:** actually finishing a real Checkout payment.
Attempted directly, as the human-in-the-loop, via browser automation (Claude in Chrome) against real
Razorpay Checkout.js — clicks land visibly on the card-entry form (confirmed by zooming into the exact
input coordinates), but neither clicks nor keystrokes register any input into the card number, expiry, or
CVV fields, reproducibly, across multiple attempts. This is dev-logs/006/007's "headless Checkout is
blocked by hCaptcha + Sardine" finding, reconfirmed here from a different angle: even a genuine
(non-headless) browser driven by an automation tool hits the same wall — Razorpay's bot-resistance is
working as intended against automated input, not merely against a missing browser chrome. Consistent with
dev-logs/007's own framing: this is the human-present gate B4 asks for, not a shortfall to route around.
**Deposit captured / both authorisations left `authorized` end-to-end still needs a human at a keyboard**
— exactly the same limitation dev-logs/006's three fixture payments and dev-logs/012's "not driven against
the deployed environment" note already named, just now hit from the automation side instead of the manual
side. The mechanism (link creation, page rendering, order correctness) is proven; the last step — a human
actually typing a card number — is not something this session can do for itself, by design.

## Carried forward

1. **A human still has to complete the actual Checkout payment** — confirmed unautomatable from this
   session, by design (see above). The three-legs-authorized proof against real Razorpay needs the user
   (or a future session with a human at the keyboard) to open the three links this slice's own live probe
   produced and pay them. Everything up to that point is proven; that one step is not.
2. **The narrow residual duplicate-order risk isn't fully closed, only sharply reduced.** A retry now
   prefers the strongly-consistent `pending_payment_legs` read, which handles the realistic case (a human
   takes real time to pay). If `pending_payment_legs` is somehow itself not yet visible to a retry (e.g. a
   read against a stale replica, not something observed here) the retry would still fall back to
   Razorpay's own receipt lookup and could in principle race the same lag. Not engineered around further
   here — the fix already closes the only case actually reachable through this codebase's normal write
   path (our own Postgres read, same transaction discipline every other read here already uses), and a
   belt-and-braces fix against a replica-lag scenario that hasn't been observed would be solving an
   imagined problem, not a real one.
3. **Test-account clutter.** The live tests and manual probes run this session created several real
   (harmless, test-mode) orders in the connected Razorpay account beyond the two long-lived fixtures
   `razorpay-payment-provider.live.integration.test.ts` already documents owning. Not cleaned up —
   Razorpay test-mode orders cost nothing and expire on their own; noted here for anyone who goes looking
   at the dashboard and wonders where they came from.
